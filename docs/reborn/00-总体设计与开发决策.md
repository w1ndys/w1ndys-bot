# W1ndys Bot 重生版：总体设计与开发决策

> 本文基于对旧 Py 版（`w1ndys/w1ndysbot`，28 个模块）和现行 Go 版（`w1ndys/w1ndys-bot`）的完整阅读，回答三个战略问题，确定新项目架构，并把开发拆成 09 个可独立验收的步骤 spec。
>
> 旧配置全部作废，本项目推倒重来。下文所有"平台"指新项目的基础能力，所有"插件"指编译期内置插件。

## 0. 三个战略问题的决策

### Q1：WebUI 是否太复杂？

**决策：WebUI 保留，且作为唯一主管理面；但通过"通用记录表"平台能力把 80% 插件的 WebUI 成本降为零。**

- 单管理员、10-20 个插件、数据表格为主，WebUI 是正确的管理面。QQ 文本命令只适合低频操作。
- 痛苦的根源不是 WebUI 本身，而是"每插件 = 迁移 + Repository + Service + 专属 API + 专属 Vue 页"五件套。
- schema 自动渲染失败的教训：**不要做万能引擎**（嵌套对象、任意类型、表达式、关联、动态表单），只做**窄契约**（扁平记录表，见 §2）。
- 补充手段：CSV 导入导出。批量数据用 Excel/表格工具编辑后一次导入，直接消灭"手打文字"痛点。

### Q2：Go 是否不如 Python 方便？

**决策：保留 Go。**

- 核心诉求是"插件加载机制 + 数据管理"，与语言无关。Py 版的痛点（每模块手写 sqlite、手打命令）在 Python 中同样存在。
- 插件即代码、编译期注册：Go 强类型让插件契约（Spec、记录表列定义、配置 Schema）可审查、可测试，改错编译不过。
- 单二进制部署，无 Python 多版本环境问题；goroutine 天然匹配"WS 收包 + worker + 定时任务"。
- 结论：Go 的"不方便"主要在写样板代码——这正是通用记录表要消灭的部分。

### Q3：除了 WebUI 还有其他更方便的形式吗？

| 形式 | 评估 | 结论 |
| --- | --- | --- |
| QQ 文本命令 | 手打文字，批量数据不可行 | 保留为应急/即时查询入口 |
| QQ 卡片/按钮 | 群内不支持卡片 | 不可行 |
| 临时 URL 页面 | 群内公开不安全；私聊给管理员的一次性授权链接（短时、单次）可用但仅限特定流程 | 可选补充，非主方案 |
| **WebUI + 通用记录表 + CSV 导入导出** | 单管理员 10-20 表格型插件的最优解 | **主管理面** |
| CLI / 配置文件 | 适合开发者，不适合管理员 | 不作为管理面 |

## 1. 核心洞察：成本根源与解法

旧模式每个数据表插件 = 五件套。你尝试 schema 自动渲染失败，是因为**通用性太强**。

解法：平台提供一次性的**通用记录表能力**，覆盖一个窄契约：

```text
记录 = 群号 + 若干列（string/text/integer/number/boolean/enum/time）
     + created_at/updated_at + version（乐观锁）
操作 = 分页列表 / 搜索 / 新增 / 修改 / 删除 / CSV 导入导出
约束 = 每群唯一键组合 / 必填 / 枚举取值 / 类型校验
```

插件只需：

1. 用 Go 结构体声明表定义（列、唯一键、排序、是否只增）——编译期、可审查；
2. 写自己的消息处理逻辑（观察器/命令/后台任务）——有趣的那 20%；
3. 可选的自定义校验钩子。

平台自动获得：一个迁移、一个通用 Repository、一组通用 REST API、一个通用 Vue 页面、CSV 导入导出、审计。

**这不是万能低代码引擎**，红线：

- 不接受客户端传入的表名、列名、排序片段、过滤表达式或 SQL；
- 不执行插件提供的组件名、URL、HTML、脚本；
- 嵌套对象、工作流、外部副作用、复杂关联一律走专属插件路径（Spec 08）；
- 唯一键冲突、乐观锁、群隔离、审计全部由平台保证。

**窄契约 + 明确逃逸口**，就是与上次 schema 方案的本质区别。

## 3. 总体架构

```text
NapCat 群事件 → 反向 WebSocket → Dispatcher
  ├─ 命令匹配 → 全局 Ready → 群 Enabled → 代码身份 → 允许角色 → Handler
  ├─ 未命中命令的群事件 → 观察器门禁（全局 Ready → 群 Enabled）→ Observer
  └─ 后台任务 → 全局生命周期启停 → 每个群副作用前重查群门禁

管理面（单管理员）：
  WebUI（主入口）→ 平台 API
     ├─ 通用记录表 API（Spec 06 一次实现，所有记录表插件复用）
     ├─ 标量配置 API（通用）
     └─ 专属插件 API（仅复杂插件，Spec 08）
  QQ 应急命令（次入口）→ 复用同一 Service（Spec 08）
```

单一事实来源：

```text
代码：插件身份、命令、触发词、作用域、允许身份、记录表列定义、配置 Schema
数据库：管理员可变状态（开关、配置值、记录数据、审计）
WebUI：主要管理入口；QQ：最小应急入口
NapCat API 格式：唯一权威 = https://github.com/NapNeko/NapCatDocs/tree/main/src/api（按版本目录）
NapCat 源码：实现细节核对 = https://github.com/NapNeko/NapCatQQ（如事件上报类）
```

安全基线（沿用现行版且必须保持）：

- 所有插件、所有群默认关闭；无状态记录等同关闭；fail-closed。
- 私聊不进入普通插件执行链；超级管理员不隐式绕过命令授权。
- 群 ID 只信已验证路径/上下文，不信任 Body。
- 启停使用乐观锁 + 审计；启用完成前不接流量，禁用先停止准入再排空在途调用。
- 时间统一 UTC（`TIMESTAMPTZ`）；WebUI 展示层按浏览器时区转换。
- 密钥仅入未跟踪的 `.env`：`DB_PASSWORD`、`NAPCAT_TOKEN`、≥32 字节 `JWT_SECRET`、≥12 字符 `WEBUI_PASSWORD`、`SUPER_ADMIN_QQ`。

## 4. 关键技术决策（ADR）

| # | 决策 | 理由 | 备选与取舍 |
| --- | --- | --- | --- |
| 1 | 语言用 Go | 编译期插件契约可审查；单二进制部署；goroutine 天然适配 WS+worker | Python：原型快但架构痛点不变 |
| 2 | 编译期内置插件 | 插件均已知、可审查；无动态加载复杂度 | .so 动态加载：仅当第三方分发成为现实 |
| 3 | 通用记录表：JSONB 单表 + 代码声明列 | 覆盖 80% 扁平表格，零迁移、零专属页 | 生成真实 SQL 表：约束更强但迁移管理复杂，仅在需要强关系/跨表 join 时用（专属路径） |
| 4 | PostgreSQL 单一存储 | 与现行版一致；JSONB 支持记录表；事务 + 审计可靠 | SQLite：部署简单但多写入/WebUI 并发弱 |
| 5 | 标量配置走通用配置表单 | 仅 string/multiline/integer/boolean/enum/secret | 完整 JSON Schema：太重，已失败过 |
| 6 | 门禁默认全关 + fail-closed | 安全基线 | 默认开启：风险不可接受 |
| 7 | 管理员单账号（JWT + 环境变量密码） | 单管理员场景最简 | 多账号 RBAC：过度设计 |
| 8 | 乐观锁 + 审计覆盖所有写操作 | 防并发覆盖、可追溯 | 无锁：数据竞争 |
| 9 | 运行快照 + 数据库分离 | 消息热路径零 SQL；**DB 是唯一真相源，内存是只读快照**；写操作先落库、成功后再原子刷新快照，禁止内存反向写回 | 热路径查库：阻塞、耦合 |
| 10 | 可读性优先，拒绝过度抽象 | 人工可读性是第一标准；重复点出现 2-3 次后才抽象；泛型/类型约束把规则固化为编译期检查 | 提前抽象：不可读、难维护 |
| 11 | HTTP 框架用标准库 net/http | 管理 API 路由简单、低并发；Go 1.22+ `ServeMux` 原生支持方法路由与路径参数；零依赖、可读性第一；避免 gin/echo 的反射绑定与编译期约束冲突 | gin/echo/chi：额外依赖、反射绑定、性能优势在本场景用不上 |
| 12 | 消息处理并发：全局受限 worker pool + 乐观锁兜底 | 事件入队后 worker 并发处理，不做每群串行、不保证同群顺序，保及时性；同群/同记录竞态由 DB 乐观锁（version）+ 唯一约束兜底 | 每群串行：前序消息阻塞拖累后续，牺牲及时性 |

### 开发原则（最高优先级）

1. **人工可读性第一**：代码必须让下一个开发者不借助文档就能读懂意图。不为高级感引入抽象层、间接跳转或多余接口。
2. **先直白，后抽象**：先写直白代码；出现至少 2-3 个真实重复点后再提取公共抽象（与"先沉淀真实页面再抽公共组件"一致）。
3. **编译期约束优先**：能用 Go 泛型、类型约束、强类型 DTO 和代码声明表达的规则，一律在编译期固化，让不合规用法在 `go build` / `go vet` 阶段报错；禁止用反射、`any` 或运行时字符串拼接绕过类型系统。
4. **可扩展性来自窄契约**：宁可让契约窄而清晰，不用层层封装假装灵活。

## 6. 如何按 Spec 开发

每个 Spec 是一个可独立验收的开发里程碑。依赖关系：

```text
01 骨架 ─→ 02 NapCat ─→ 03 插件运行时 ─→ 04 数据层与管理面
                                              │
                                              ▼
                              05 平台 WebUI ─→ 06 通用记录表 ─→ 07 记录表插件示例
                                                                   │
                                                                   ▼
                                             08 专属复杂插件 + QQ 应急 ─→ 09 打包部署与验收
```

- 建议从空白仓库开始，按 01→09 顺序开发；每个 Spec 完成即提交（一次提交一个逻辑变更）。
- **插件迁移策略**：初期仅验证框架——Spec 03 做 `echo`、Spec 07 做最小记录表插件 `keyword_reply`；原 Py 版插件（FAQ、违禁词、签到等）待框架稳定后按需求逐个迁移（先写设计卡分类：记录表/标量配置/专属，再按对应路径实现）。
- 每个 Spec 的验收清单必须全部通过才进入下一个；失败项要有具体修复记录。
- 提交信息遵循全局规范：`类型(内容): [emoji] 中文描述`。
- 每个 Spec 开发前先写设计卡（插件 Key、命令、作用域、状态归类、WebUI 需求、外部副作用）；开发后做独立复核（需求符合度、权限与校验、越群、事务、快照一致性、并发、资源清理、敏感信息、错误处理、测试遗漏）；**每个 Spec 结束后必须调用独立 subagent 做风格一致性审查**，逐项核对是否符合 AGENTS.md「代码可读性与编译期约束」与项目编码风格，防止多次开发产生多种风格。
